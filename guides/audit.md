# Audit

`mj-zana/audit` (2.2) keeps the revisions of edited content: who changed a
page, when, what changed, and a way back. Each record keeps one history per
locale, so a French correction does not touch the English text.

```
composer require mj-zana/audit
```

## Revisions

<!-- example: examples/guides/audit.php#revisions -->
```php
// AuditServiceProvider stores revisions in the database, with the signed-in user as author.
$revisions = new Revisions(new InMemoryRevisionStore(), static function () use (&$author): string {
    return $author;
}, static function () use (&$now): int {
    return $now;
});

$revisions->record('post', '42', 'fr', ['title' => 'Lancement', 'body' => 'Bientôt.']);
[$author, $now] = ['bob', $now + 3600];
$revisions->record('post', '42', 'fr', ['title' => 'Lancement', 'body' => 'Aujourd’hui !']);

foreach ($revisions->history('post', '42', 'fr') as $revision) {
    echo "v{$revision->version} by {$revision->author} at ", gmdate('H:i', $revision->createdAt), "\n";
}

[$latest, $previous] = $revisions->history('post', '42', 'fr');
echo 'Changed: ', json_encode($latest->diff($previous), JSON_UNESCAPED_UNICODE), "\n";

$data = $revisions->restore('post', '42', 'fr', 1);   // save $data to the post yourself
echo 'Restored: ', $data['body'], ' (now v', $revisions->latest('post', '42', 'fr')?->version, ")\n";
```

<!-- example: examples/guides/audit.out -->
```text
v2 by bob at 10:00
v1 by ada at 09:00
Changed: {"body":["Aujourd’hui !","Bientôt."]}
Restored: Bientôt. (now v3)
```

Rules worth knowing:

- **Record after saving.** Call `record()` with the content as it now is;
  the history is newest first.
- **Unchanged content records nothing.** Saving a form without changes
  returns the latest revision instead of adding one.
- **Restoring is a new revision.** `restore()` returns the old data and
  records it as the latest version; nothing is rewritten, so the history
  stays complete. Saving the data on the record is up to you.
- `diff()` lists the changed fields as `[new, old]`.

## In an application

Register `AuditServiceProvider` after `DatabaseServiceProvider` and create
the table in a migration:

```php
DatabaseRevisionStore::createTable($connection);   // 'audit.table', default audit_revisions
```

Inject `Zana\Audit\Revisions` in your controllers or handlers. With the
security package installed, the author is the signed-in user's
identifier; otherwise pass `author:` to `record()`.

To keep the history of the screens generated by `make:crud`, record a
revision per locale after each save (see
[a back office](../cookbook/back-office.md#4-keeping-a-history)).

## New in 2.15: the security audit log

Beside revisions, audit keeps an append-only record of sensitive actions:
sign-ins, refunds, payout account changes. It is there for disputes and for
the data-protection rules. Turn it on, and create its tables:

```php
// config/audit.php
return [
    'log' => [
        'enabled' => true,          // record security events; check the table
        'chain' => true,            // hash chaining (off by default)
        'retention_days' => null,   // keep entries forever; or, e.g., 3650
    ],
];
```

```
php bin/zana audit:install-log
php bin/zana migrate
```

With [security](security.md) and [events](events.md), sign-ins, failed
sign-ins, sign-outs and password resets are recorded:

<!-- example: examples/guides/audit-log.php#events -->
```php
// With audit.log.enabled, the provider adds this listener: mj-zana/security's sign-in events go
// into the log. SessionLogin dispatches them.
$events = new EventDispatcher((new ListenerProvider())->listen(SecurityEvent::class, new SecurityEventsRecorder($store)));
$events->dispatch(new SignInFailed('amani@example.com', SignInFailed::INVALID_CREDENTIALS, '198.51.100.7'));
$events->dispatch(new SignInSucceeded('7', '198.51.100.7'));
```

Record your own actions with `AuditLog`:

<!-- example: examples/guides/audit-log.php#record -->
```php
// In an application, AuditLog is scoped: the actor is the signed-in user, and the client address and
// correlation id are the request's.
$audit = new AuditLog($store, static fn (): string => '7', static fn (): string => '198.51.100.7');
$audit->record('payout.account_changed', subject: 'organizer:12', details: ['bank' => 'Rawbank']);
```

Or mark a [mediator](mediator.md) command, and add `AuditedBehavior` to
`mediator.behaviors`. The command is recorded once its handler returns, with
only the fields listed. A card number in the same command is never recorded:

```php
#[Audited('order.refund', subject: 'orderId', details: ['orderId', 'amount'])]
final readonly class RefundOrder
{
    public function __construct(public string $orderId, public int $amount, public string $cardNumber) {}
}
```

### The hash chain

With `audit.log.chain`, each entry stores the hash of the one before it.
An entry that was changed, inserted or removed outside the application
breaks the chain:

<!-- example: examples/guides/audit-log.php#verify -->
```php
// php bin/zana audit:verify. Someone with database access changes the bank of entry 3:
echo 'Chain intact: ', $store->verify()->intact ? 'yes' : 'no', "\n";
$db->table('audit_log')->where('sequence', 3)->update(['details' => '{"bank":"Elsewhere"}']);
$report = $store->verify();
echo 'Chain intact: ', $report->intact ? 'yes' : 'no', " (entry {$report->brokenAt}: {$report->problem})\n";
```

<!-- example: examples/guides/audit-log.out -->
```text
#1 security.sign_in_failed {"login":"amani@example.com","reason":"invalid_credentials"}
#2 security.sign_in by 7 on user:7 {"method":"session"}
#3 payout.account_changed by 7 on organizer:12 {"bank":"Rawbank"}
Chain intact: yes
Chain intact: no (entry 3: The entry was changed after it was written.)
```

- **What the chain proves:** it catches a row changed, added or removed,
  but not by someone who also recomputes the hashes. They use no secret, so
  someone with write access to the database and Zana's source can rewrite
  the log. Where the log must stand against database administrators, keep
  `audit:verify`'s output and exports off the server. A keyed chain is
  planned for 2.20.
- **Append-only:** the API has no update and no delete. You can also deny
  the database user `UPDATE` and `DELETE` on `audit_log`.
- **Checks:** `check` verifies the newest 1,000 entries, and
  `audit:verify` checks them all, exiting with code 1 when the chain is
  broken.
- **Concurrent requests** append one at a time to the chain. This is tested
  with four processes on SQLite, MySQL and PostgreSQL.
- **Retention:** `audit:prune` deletes entries older than
  `audit.log.retention_days`, oldest first, and the rest of the chain still
  verifies. Without that setting, nothing is ever deleted.
- **Reading:** `audit:log --action=security.sign_in_failed --limit=20`, and
  `inspect audit-log`.
- **No secrets:** an entry cannot be changed, so record only what a dispute
  needs.
